## 1. 目的と問題認識

AIエージェントが、情報を文章化して画面へ配置することに過度に依存せず、視覚的な表現と構成を自ら考案・制作し、許可された範囲で既存成果物を発展させられる環境を実現する。単にAI Slopを排除するのではなく、優れたデザインを自然に生み出せる制作能力を拡張する。エージェントの能力・裁量・自発性への過度な依存と、人間による逐次指示の必要性を減らす。

問題として観測されてきたのは、説明文主体、見出し＋説明の反復、同型カードの羅列、単調な縦積み、製品・成果物の実体より説明を優先する構成、装飾的なアイコンで文章を補うだけの表現、主役と補助要素の区別の不足、個々のcomponentは整っていても全体の構図が成立しない状態である。これらは現時点では定性的な問題報告であり、頻度や因果寄与の測定結果ではない。

カード、文章、反復、単列、均等なグリッドの使用自体を欠陥としない。画面の目的・内容・利用状況にかかわらず既定の表現が選択されることが問題である。AI生成であること自体も品質判定基準ではない。AI Slopという語を用いる場合も、具体的な情報・表現・構図・機能上の観測へ分解する。

例えば、六つの機能が存在しても六つの等価なカードを作る必要はない。機能の実体を統合された操作環境として見せる、主要な成果物に視覚領域を配分し関連情報を補助する、といった別の表現・構成が成立し得る。

## 2. 原因仮説（未実証）

| 仮説 | 内容 | 典型的な観測候補 |
| --- | --- | --- |
| Representation Bias | 情報に適した媒体ではなく文章を既定値として選ぶ傾向 | 操作を説明するだけ、時系列を文章化、成果物そのものを見せない |
| Composition Bias | 言語上の情報階層・機能一覧・component構造をそのまま空間構造へ写す傾向 | 同型カード化、縦積み、異なる重要度への同面積配分 |
| Execution Bias | 制作・探索・検証の摩擦や予算等によって、より容易に完了できる表現へ収束する傾向 | 素材未探索、描画未実施、生成失敗後の断念、改善省略 |
| Prior Bias | 学習・既存例・プロンプト・既定component等から得られる強い構造的事前分布やアンカーが、選択を平均的な解へ引き寄せる可能性 | 素材やツールが揃っていても慣習的なLP構造などへ固定される |

四つは排他的な原因分類ではない。RepresentationとCompositionは出力・設計行動の傾向を記述し、ExecutionとPriorはそれを生む可能性のある要因も含む。相互作用し得る。事前分布そのものを外部ログから直接観測することはできない。ツールがあるのにカードを生成した事実だけで、Prior Biasが原因と断定してはならない。具体的に何を参照し、何が利用可能で、何を試みたかを観測し、必要なら参照例・構造アンカーや制作摩擦を独立に変えた比較で検証する。新しい例への固定や単なるreference cloneも失敗である。

スキル未発火、知識不足、実行環境の制約、判断誤り、予算、学習上の傾向を混同しない。寄与率も支配的原因も未確定。表現を増やしても構図が凡庸な場合、構図を改善しても説明への依存が残る場合、両者を知っていても実行しない場合を区別する。

## 3. 不変の設計原理：意味と空間構造を区別する

情報の論理構造と、その情報を知覚・利用させるための視覚的・空間的構造は同一ではない。

- 意味的側面：内容・事実・機能・操作・優先度・論理関係・成立させたい体験。
- 視覚的側面：形状・位置・寸法・色・コントラスト・密度・視覚的な強さ・余白・整列・グルーピング・主従・リズム・時間変化。

テキスト、画像、図形、UI、映像は、構図の設計において共通の視覚的な存在として扱える。文章の意味を読むことだけで配置を決めず、見出し・段落も視覚的な形態として他の素材との関係を設計する。これはテキストの実際の画像化や、意味の消去を要求するものではない。アクセシビリティ、可読性、選択、検索、コピー、翻訳、編集、動的更新等を保持する。操作の意味と空間上の優先度も対応させる。

Representation（何で表現するか）とComposition（どのような空間関係で構成するか）は独立して評価し、制作時には相互作用を許す。先に一方を完了させる固定工程は必要ない。表現媒体の貧困を幾何学的最適化へすり替えない。構図の問題を画像数の増加へすり替えない。

グリッドは共通座標系であり均等分割を強いる檻ではない。近接・類同・図と地・階層・プロポーション・リズム・余白・光学的整合・バランス等を、具体的な関係と操作として扱う。例えばグループ内外の距離は意味的な関係に対応し得る。これらを普遍的な固定数値や美的法則へ還元しない。見かけの境界はDOM矩形と一致しないことがある。

ドキュメント、書籍、コード、ターミナル、表、設定、検索結果、タイポグラフィ作品では文字を主役とする合理性がある。テキスト量や非テキスト面積の最大化・最小化は目標ではない。

### 視覚的抽象化は検証候補であり不変原理ではない

意味と空間構造の区別は維持するが、VLMへ文字をマスク・矩形・ぼかしとして提示する Perceptual View はその実現手段の一候補に留める。人間の視覚設計原理の妥当性は、VLMに対する特定入力変換の有効性を保証しない。学習分布外の入力による認識悪化や均等・対称グリッドへの偏りもあり得る（未検証）。

候補手段は、通常の描画（Normal View）、意味を弱めた知覚表現（Perceptual View）、領域・整列・余白の観測（Geometry View）である。知覚表現ではサイズ・ウェイト・コントラスト・行長・字間行間・密度・階層・画像との関係を可能な限り保持する。単一色の矩形へ潰すことで階層を失ってはならない。DOM、軽量なマスクやぼかし等は必要性に応じて比較する。通常画像を置き換える前提にせず、効果がない／悪化する場合は採用しない。それでも意味と空間の区別という原理は維持する。

## 4. 品質の上限と下限

Quality Floor（必要な品質の下限）と Design Capability（より優れた表現を生む能力）を独立の目的とする。

| 観点 | Quality Floor | Design Capability |
| --- | --- | --- |
| 目的 | 許容できない欠陥・回帰を防ぐ | 表現・構図・体験の可能性を拡張する |
| 主な手段 | 契約検査、検出、修正、検証 | 素材制作、表現選択、空間設計、探索、摩擦低減 |
| 評価 | 必須情報・機能・可読性・整合性・アクセシビリティ | 伝達力・意図ある構図・固有の魅力・体験 |
| 効果 | 不適切な選択を制限する | 利用可能な選択肢を広げる |

規則への準拠は優れたデザインの十分条件ではない。下限保証だけでは凡庸な成果物を安定して生む可能性がある。上限拡張だけでは基礎品質は保証できない。両者を補完させるが、下限側の検出器を上限側の制作目的にしてはならない。ルールは最低限を支えるものであり、最大限の表現を規定しない。正当な仕様・ブランド・操作上の制約は守る。標準的で習熟しやすい解を最適とすることも認め、奇抜さや独自性を一律に強制しない。

初回生成能力と事後修正能力を区別する。初回生成とは外部の追加検査・差し戻し前の通常の自律制作結果（制作中の自主的な描画・修正を含み得る）。初回から適切な表現を選んだことと、外部指摘で修正できたことを同一視しない。上限の改善は初回に限られないが、初回品質は制作環境が自然な選択を変えたかの重要な証拠である。

## 5. 解決仮説：制作の選択肢と環境を変える

既存の design-discipline、design-intent、layout-system、visual-hierarchy、information-density、data-visualization、diagram-design、composition-review、visual-review、design-system-enforcement 等には既に多くの原理がある。特に design-discipline は要求の単純なcomponent化の回避、実物による構造探索、成果物による評価を扱う。新たな自然言語指示の追加を既定の解としない。

以下の三つは必要性を検証する機構の概念であり、独立システム、固定パイプライン、実装承認ではない。

### 5.1 Visual Primitives：上限側

情報や体験を表現する手段（比較・時系列・分布・関係・階層・状態・操作デモ・成果物・グラフィック・タイポグラフィ等）を容易に利用できる環境を検討する。既存のSVG、CSS、Canvas、図表ライブラリ、図解、preview、captureを優先する。

新規制作と既存改修の双方で Actual（実物・実データ）、Fixture（管理されたサンプル）、Model（仕様に基づく模式表現）、Prototype（実行可能な試作）、Original（新規制作素材）を許容する。試作・仮データを実製品・実績として偽装しない。既存素材がないことを即座に文章への回帰やBLOCKEDの理由にしない。

低レベルの描画操作は自由度が高いが摩擦が大きく、完成ページのtemplateは容易だが均質化リスクがある。意味的な表現単位を候補としつつ、その粒度・API・配布形態を事前に決めない。既存技術があるのに使われない理由（認知、選択、導入、記述量、描画確認、失敗復旧、token統合、初期の文章化、予算等）を先に観測する。既存ツールで足りれば独自wrapperを作らない。Prior Biasが関与する場合には例示・アンカーの差し替えや参照の多様性も比較対象になり得る。

### 5.2 Visual Composition：上限側

テキストを含む視覚的存在の空間関係から、言語構造に従属しない構図を考案する能力を拡張する。整列、グループ化・分離、空間配分、主役の昇格、領域の統合・分割、読み順、反復の再編、レスポンシブな再構成等は具体的な構成操作の候補である。観察方法だけで生成能力が高まるとはみなさない。

構造選択が重大な場合、実際のコード・描画環境における可逆的な候補探索を検討する。候補数を一律に強制せず、捨てHTMLと本実装の二重制作を前提にしない。採用可能な差分や既存component・fixtureを利用する。初期案への固定の回避は目的に対する実物の比較で判断し、templateの差し替えや無意味な奇抜さに還元しない。

### 5.3 Structural Feedback：主に下限側

同型領域の反復、説明文への面積集中、単調な空間構成、主要素材の欠落・過小配置、空間関係の不整合等を観測して改善へ接続する。DOM・BoundingBox・ComputedStyle・描画は候補手段。構造的特徴は欠陥確定ではない。DOMだけでは画像内部の文字・素材の意味・光学的な境界等を判定できない場合があるが、その頻度も未測定である。

Hard Constraints（必須情報・機能の欠落、定義済み契約違反等）と Structural Findings（文脈に依存する問題候補）を区別する。カード数、非テキスト比率、テキスト占有率等の一般的な固定閾値を美的Hard Gateにしない。無関係な画像、文字の焼き込み、必要情報の削除、形式的DOM変更で指標を攻略する行為を改善とみなさない。検出器は検討・具体的な修正の契機であり、優れた表現を生成する機構の代替ではない。

三つの機構は相互補完するが、初回制作を事後検出に従属させない。

## 6. 自律性・リファクタリング・権限

自律性とは必要な制作・探索・改善を人間の逐次指示なしに遂行する能力であり、変更scopeやプロダクトの方向性を自ら拡大する権限ではない。創造的判断へのモデル依存を完全には排除しない。スキルの偶然の選択、描画能力を思い出すこと、制作摩擦、自己評価、工程省略への過度な依存を減らす。

- Corrective Refactoring：確認された欠陥・不整合・下限割れを回復する。自動起動の対象にできるが、検出候補だけで欠陥と断定せず、変更は既存の権限・Issue・対象scopeの範囲内。scope外の欠陥は証拠を記録して適切な修正作業へrouteする。
- Expressive Refactoring：基礎品質を満たす成果物についても、より適した表現・構図・体験を探索する能力。通常の新規設計に含まれる探索、または明示的に許可されたデザイン改善・再設計タスクの範囲内で自律的に行う。正常な既存画面への無許可の大改修・自動変更を起動しない。監査で改善可能性を提案することと、実際に改修することは別である。

許可された作業内の可逆的な通常判断まで逐次承認へ戻さない。ブランド、主要導線、情報優先度、外部契約等の重大な方向転換は既存の決定・権限境界を尊重する。探索・修正は予算と改善見込みで停止し、無限チャーンを避ける。

新規設計と既存改修は情報、表現、素材、空間関係、成果物確認を共通に扱う。既存改修ではさらに現行機能・情報・設計意図・利用者の習熟・互換性・保守性を保持する。汎用的なソース逆変換を前提にしない。

## 7. 評価と保証の境界

幾何学的な測定は構造を説明するが、美的品質を証明しない。AIレビューの独立性は有益な可能性があるが、独立性と妥当性は別である。モデル間の共通バイアス、均等な構造への偏りは検証課題であり、存在・程度を確定しない。

抽象的な点数や「洗練」の形容だけで判定せず、初見で認識されるもの、目的の理解、必要情報の取得、関係の理解、操作の成否、具体的な改善を観測する。初期評価の校正に独立した人間の比較を利用できるが、日常作業の逐次受入に置き換えない。AI評価・人間評価・決定的検査・自己評価を区別し、未実施の評価を合格扱いしない。

Web/GUIは静止画だけではない。画面幅、データ量、文字長、状態、スクロール、フォーカス、操作、テーマ等に応じて維持される関係を扱う。既存projectの品質profileに従い、通常ticketは影響範囲に応じた局所検証、包括的検証は専用タスクやrelease candidate freeze後に集約する。人間の細かな確認や全体E2Eを全ticketに追加しない。release承認の境界を変えない。

## 8. 既存基盤と着工の判断

本研究の対象は初期のWeb UIであり、結果を他媒体へ無条件に外挿しない。

- design-skills：設計知識、表現・構成・探索、artifact review の正本。
- aude-skills（旧称 project-init）：能力の選定・利用可能性、実行・品質保証・権限・delivery の基盤。
- 対象project：製品要件、素材、コード、描画・検証環境。

[#170](https://github.com/rebuildup/design-skills/issues/170) の design-discipline trial と [project-init#129（現 aude-skills#129）](https://github.com/rebuildup/aude-skills/issues/129) の採用判断を尊重する。既存の [#195](https://github.com/rebuildup/design-skills/issues/195) 反例検証、[#197](https://github.com/rebuildup/design-skills/issues/197) 機能美レビュー、[#199](https://github.com/rebuildup/design-skills/issues/199) 実描画レビュー連携の成果と重複させない。

現時点で新規 Skill、既存 Skill の強制activation、Visual Primitives、Perceptual View、検出器、workflow、project-initの方針改変を着工・採用しない。まず Experiment 0 の証拠で必要な介入を選ぶ。将来Skillが必要と判明した場合も、既存の理論と重複する指示を増やすことを既定値とせず、必要な能力の利用・routing・摩擦低減など観測された問題に対応させる。

現時点で採用しない設計：汎用Visual IR、ピクセル単位の視覚重量最適化、広範な画像処理、万能な構図ソルバー、任意React/CSSへの逆変換、固定YAML契約、必須多段階状態機械、重複試作、普遍的な美的Hard Gate、完成形templateの一律導入、汎用実験runner、AI美的スコアを真値とする方式。具体的な未解決問題に対する必要性が実証された場合だけ再検討する。

## 9. Experiment 0：現行環境の観測

理論と実証を対立させない。比較条件と評価・採否の基準は事前に定義するが、介入の実装仕様やExperiment 1以降の比較群は初期観測より先に確定しない。初期実験は原因候補の発見と切り分けのためであり、一般的な因果・発生率・美観の優劣の統計的証明ではない。

| Task | 初期状態 | 試行数 |
| --- | --- | --- |
| T1 新規製品紹介 | 製品仕様あり、完成画面・素材なし | 3 |
| T2 新規dashboard | 構造化fixtureデータあり、完成UIなし | 3 |
| T3 既存UI改善 | 既存コード、素材、機能あり。明示的に許可された改善scope | 3 |

計9試行。文章閲覧・コード・設定等、正当なテキスト主体の画面は正常な対照例として評価に含める。実際の生成試行を追加するか既存対照artifactを用いるかは試験開始前に記録する。対照例を主9試行に混ぜない。

各task内で要求、model/runtime、project-init/design-skillsの利用revision、初期コード、fixture、素材、利用可能ツール、権限、実行予算、描画条件、評価条件を固定する。独立した開始状態・sessionを使用する。既存Skillは通常の運用条件で利用可能にし、実際に読まれたかを観測する。強制loadを比較する場合は別条件とする。試験対象の既存productのrelease/本番へ実験変更を流さない。

既存ログ、Git差分、worktree、既存capture手段、手動観測、必要最小限のスクリプトで実施する。専用runnerや構造化ログ基盤を新設しない。初回passの境界を事前に記録し、最初の描画と外部の追加介入前のcandidate、最終描画を可能な範囲で保存する。取得できない証拠はunknown/unverifiedと記録し、実施したと推測しない。

最低限の証拠：trial ID、固定条件への参照、利用可能/読込済みSkill、利用可能/使用済みツール、素材探索・生成試行・エラー、表現と構図の選択、初回と最終の実物・対応するrevision、検証と修正の履歴、時間・モデル消費（取得できる場合）。初回から適切だった場合も保存する。

観測は次の二軸を分ける。
- 基礎品質：必須情報・機能・可読性・整合性・アクセシビリティ等。下限割れの具体的根拠を記録。
- 表現能力：媒体の適切性、構図、伝達力、対象固有の魅力、体験。下限を満たしているが凡庸である状態を区別する。正常な標準的解を無理に失敗扱いしない。

制作中の事実と原因推測を区別する。例えばSVG未使用は事実になり得るが、面倒だった、または事前分布が強かったという因果は未確定。比較・追加probeが必要なら明示する。

### 次の判断

| 観測 | 後続で検討する介入 |
| --- | --- |
| Skill未読込 | 既存の発火・routingの検証 |
| 描画手段があるが利用されない | 認知・表現選択・制作摩擦・アンカーの切り分け |
| 素材制作を試み失敗・断念 | 具体的な摩擦を除くVisual Primitives |
| 素材は十分だが構図が弱い | Visual Composition、構造探索、参照方法 |
| 最初の構造へ固定される | 可逆的な構図探索、アンカー比較 |
| 問題を認識しない | Structural Feedback／評価方法 |
| 問題を認識するが修正しない | 必要最小限の実行保証 |
| 基礎品質は高いが表現が凡庸 | 上限側の生成能力を独立に検証 |
| 既存環境だけで十分 | 新機構を導入しない |

後続比較では同じ要求・開始状態・予算・改善機会を統制し、初回品質と修正後品質、表現と構図の寄与、基礎品質、追加指示回数、時間・消費・保守性を分ける。必要な場合のみ素材供給、構成支援、feedback、参照例の介入を個別または組み合わせて試す。指標攻略や正常なUIの破壊が起きる機構は棄却または縮小する。九試行で不明な事項は不明のまま残す。

## 10. 未解決と採否の原則

原因仮説の寄与、既存Skillの機能不全条件、既存描画手段の利用摩擦、適切な抽象度、知覚入力変換の有効性、構図観察が生成へ還元される条件、AI評価バイアス、初期案への固定、必要な実行保証、品質と追加コストの関係は未解決。観測なしに解決済みとしない。

何を実装したかではなく、実際に制作行動と成果物がどう変化したかを採否の根拠とする。理論に合うからと実装を正当化せず、効果がなければ手段を撤回する。問題設定そのものが観測と合わなければ理論を修正する。優れたデザインを生む能力と必要な品質を保証する能力の両立を羅針盤とする。
